# `ai-policy`: machine-readable rules of engagement for AI contributions

`ai-policy.yaml` is a small file a project keeps in its repository to declare what it permits in AI-assisted contributions: whether AI-generated work is accepted, whether its use must be disclosed, whether an autonomous agent may open a pull request, and what AI may do in review. Coding agents, CI checks and aggregators read it before they act, so they follow the project's own rules instead of their tools' defaults; maintainers use it to work through their policy one question at a time and to show contributors where the project stands. The file states the broad shape of a policy and points at the project's prose policy for the detail. This README is the format's specification, written for maintainers, builders of agent tooling and researchers of AI policies; the format is an early proposal whose design is not settled.

## Status

**Status:** early proposal, design not settled. The format is meant to prove itself through adoption by projects rather than through a standards body, and the answers to the [open questions](#open-questions) will change its fields.

**Origin:** Lukas Kahwe Smith created the format, its survey of policies and its presets in [open-source-ecosystem/ai-policy](https://codeberg.org/open-source-ecosystem/ai-policy) on Codeberg. This repository continues that work since November 2026, with the full history of the original; its author remains a contributor and reviewer. The [discussion that led to the move](https://codeberg.org/open-source-ecosystem/ai-policy/issues/3) is on the original repository.

## Projects publish AI policies only as prose, in no fixed place

Projects increasingly publish an AI-contribution policy, but only in prose, and in no consistent place: a `CONTRIBUTING.md` section, an `AI_POLICY.md`, a `CODE_OF_CONDUCT.md`, a devguide or docs page, a wiki, an `AGENTS.md`, a `README`, even a legal page or an RFD (the [coverage survey](./coverage.md) found all of these). So an agent about to contribute, a CI check, or an aggregator has nothing machine-readable to consult; it guesses, or scrapes prose. A survey of real policies (the [CHAOSS AI-alignment moderation list](https://github.com/chaoss/wg-ai-alignment/tree/main/moderation)), analysed field-by-field in **[`coverage.md`](./coverage.md)**, shows a consistent set of dimensions beneath the surface variety, and *every one maps onto this format*. That coverage is the evidence its shape is right.

The pressure behind those policies is now recognised in policy as well as in projects. The European Commission's Open Source Observatory reports maintainers' concern that the volume of AI-generated contributions affects code quality and their capacity to review and validate changes at scale, and counts the resulting demand on maintainer capacity among the reasons open source funding remains unresolved ([OSOR, *Progress and Trends in the National Open Source Policies and Legal Frameworks*, 2026](https://interoperable-europe.ec.europa.eu/sites/default/files/custom-page/attachment/2026-10/osor-paper-on-progress-and-trends-2026.pdf)). A published policy is the cheapest lever a project has on that volume, and only a machine-readable one reaches the agents producing it. The lever has a measured effect: across 385 projects that adopted an AI policy, adoption was associated with more AI disclosure, more maintainer engagement and richer review interactions ([Chen, Zimmermann and Trinkenreich, 2026](https://arxiv.org/abs/2608.03329)).

## Coding agents read the file before opening a pull request

`ai-policy.yaml` only matters if something *reads* it, and the natural readers are coding agents:

- **A pre-flight check.** Before an agent opens a PR it reads the file the way a crawler reads `robots.txt`, except this declares *stance, disclosure, and agent-identity rules*, not crawl permissions. "May I contribute generated code here? Must I disclose it? May an autonomous agent open this PR at all?"
- **A ready integration.** The reference consumer could be an **MCP server** that serves a repo's `ai-policy.yaml` and validates a proposed change against it, so any MCP-speaking agent gets the policy without bespoke parsing. That turns "needs adoption" into "here's the integration."
- **Where agents already look.** It sits beside `AGENTS.md` / `CLAUDE.md` (which point to it), the same place agent instructions already live.
- **A sanctioned-workflow library is the other half, and one now exists.** Fedora's AI/ML SIG publishes a [skills library](https://forge.fedoraproject.org/ai-ml/skills-library) (CC BY-SA 4.0) in the [Agent Skills](https://agentskills.io/specification) open format: one directory per skill, each with a `SKILL.md` carrying YAML frontmatter and instructions. Its current skills automate compose triage, FTBFS bug search, meeting-log summarisation and Packit onboarding. A project that publishes approved agent workflows has answered in executable form part of what this file declares in prose, and "these workflows are sanctioned here" is a more useful thing to hand an agent than a restatement of the rules. Which field should point at it is [an open question](#open-questions).

## How the file helps maintainers and contributors

The same structure earns its keep before any agent reads it:

- **It structures the discussion.** "Should we allow AI?" argued in the abstract goes in circles. The format's dimensions (stance, per-`scope`, disclosure, autonomy, models, concerns) turn the debate into an agenda a project can work through one axis at a time. The distinction that makes the debate tractable at all is *adoption* versus *alignment*: Fedora's [Justin Wheeler](https://jwheel.org/blog/2026/09/ai-alignment/) separates "AI adoption", which "communicates a pre-defined, non-negotiable stance" whose goal is simply to increase usage, from "AI alignment", which "communicates that LLM-gen-AI use exists on a spectrum" to be squared with a community's existing values, norms and culture. A declaration format is only coherent under the second reading — there is nothing to declare where the answer is fixed in advance — and the spectrum is precisely what `stance`, `defaults` and `assertions[]` exist to carry. Debian's six competing General-Resolution options differ almost entirely along these axes; the format is the shared frame that makes them comparable, and a project can adopt whichever combination it lands on.
- **It manages expectations.** Contributors see what is permitted *before* they invest effort: fewer wasted PRs, fewer surprise rejections, less reviewer burnout from "extractive" AI slop. Maintainers get one referenceable boundary instead of re-litigating it per pull request, and the `statement` pointer keeps the nuance where people actually read it.

## Placement

`ai-policy.yaml` or `ai-policy.yml`, in the project's version control, normally at the repository root. Both extensions are accepted; the YAML project [recommends `.yaml`](https://web.archive.org/web/20241221084524/https://yaml.org/faq.html) where possible. If both files exist, `ai-policy.yaml` wins, and a consumer warns unless the two are byte-identical or one is a symbolic link to the other: two policy files that could disagree are exactly the ambiguity this format exists to remove. Its primary subject is **code**, but the `scope` vocabulary spans docs, translations, media, and discussion, so it applies to any contribution type.

A policy file uses only plain YAML, so that a small reader can parse it without a full YAML library: mappings and lists, in block form or in brackets, strings, numbers, `true`, `false`, `null`, comments, and blocks of text introduced by `|` or `>`; no anchors, aliases, tags, merge keys, several documents in one file, or other values spread over several lines.

Discovery, in order of preference: `ai-policy.yaml` or `ai-policy.yml` at the repository root; a peer record that points at it (for example a `publiccode.yml` `externalMetadata` entry); `.well-known/ai-policy.yaml` or `.well-known/ai-policy.yml`. Absence of the file is itself a signal: *no declared policy*, distinct from a declared permissive one and from `summary: neutral`, which declares that the project considered AI and decided it needs no rule of its own.

## What this format does not govern

`ai-policy.yaml` declares **what a project asks of a contribution**: what may be offered, and how the project handles what is offered. `scope` is a content type because the subject is a contribution; the primary consumer is something about to open a pull request, and the `review` fields tell it what becomes of the change once it does. Three neighbouring kinds of rule turn up in real policies and are deliberately out of scope, because none of them concerns a contribution's lifecycle:

- **Platform self-commitments.** Codeberg binds itself never to train on hosted code or user data. That governs the declarer's own conduct toward its users and never touches the handling of a contribution.
- **Hosting and content restrictions.** Codeberg's rule on what may be hosted, and Flathub's original policy on AI-generated applications, govern artifacts already in existence rather than contributions being offered.
- **Governance-process rules.** Fedora forbids AI scoring of code-of-conduct matters, funding requests, conference talks and leadership positions. These are decisions about people and events; no contribution is involved at any point. A project holding such a rule records it in `notes` with `exceptions: true`.

The [specificity analysis](./coverage.md#specificity-against-the-chaoss-domain-taxonomy) reaches the same boundary from the metrics side: meeting bots, infrastructure strain and training on hosted data score as ungoverned across projects largely because the wrong party is being asked, and they belong to whoever runs the meeting infrastructure, pays for the servers, or holds the data. The natural carrier is a **forge-level record**, and none exists today. Until then, the file's location and this boundary answer that question.

## Aims

The design rules below serve these aims, and are judged by them:

- **Cover the policies projects actually adopt.** The format should express the real spread of AI-contribution policies, not an idealised one. The [coverage survey](./coverage.md) is the evidence, and a policy the format cannot express is a finding to act on, not an edge case to ignore.
- **Surface the questions.** A project should be able to see from the format what there is to decide, including questions it had not thought to ask, without having to decide all of them at once. Breadth lives in the schema; a project meets only what is still open for it, through [presets](./examples/) that list what they leave unaddressed, `undecided` for what it has discussed and not settled, and the [guide](./writing-a-policy.md) for working the rest out.
- **Enable research.** Policies across projects should be studyable as data: what projects decide, why (`concerns`), what they leave open (`undecided`), and how that changes over time, recorded in one comparable vocabulary under version control. Questions that today take a manual survey like [`coverage.md`](./coverage.md) should become queries, as [mapping a labelled corpus of 281 policies](./research/hora-2026/) already shows, and the `notes` collected across adopters are themselves the corpus from which the vocabulary grows.
- **Be clearer than prose about a policy's shape.** A declaration should say more exactly than prose which questions a policy answers, how, and which it leaves open, while the judgements it delegates stay in prose and are flagged as such (`exceptions`, `notes`). The format does not aim to be clearer than prose about those judgements: what counts as *menial*, *understood* or *significant* is defined in words, and structure that pretended otherwise would be false precision. It rests on the vocabulary being defined: every value carries a definition in the [schema](./ai-policy.schema.yaml), and binding those terms to shared, dereferenceable identifiers is the open *interpretability* gap in [`machine-readability.md`](./machine-readability.md).

Coverage, surfacing the questions and research all pull towards more structure, and so against easy adoption, since every field added is one more question for an adopter. Presets, `undecided` and the `notes`-first route are how the format keeps both.

## Design principles

- **Structure only what recurs, or what a consumer must act on before submitting; point at prose for the rest.** `statement` holds the authoritative policy; `exceptions: true` says "this is a summary." Recurrence is the usual route into structure, through `notes` (below). The second route is narrower and exists because the primary consumer acts before anyone can correct it: a value earns an enum on first sight when a consumer holding only the file and the contribution must branch on it before submitting, the same test that settles [numeric thresholds](#open-questions). `disclosure: prohibited` entered this way, since an agent that adds a disclosure trailer by habit breaks the policy with every commit, and so did the `reproduced` requirement, which a submitter can check and no reviewer can repair afterwards.
- **Declare, don't adjudicate.** Fields state intent; verification (tests, review, the human `signoff`) and the fact of LLM authorship (undetectable in general) stay outside the file. Declared identity (`attestation`) is the tractable lever, not detection.
- **Resolution is per-`scope`** (a contribution's content type); `actorExceptions` is a *signal*, not a resolution layer. Full rules below in [Resolution](#resolution).
- **Development-time, not runtime.** `models` is the AI used to *build* the project, not AI the product ships.
- **Stance is permission, not preference;** agent autonomy is a separate axis, never a stance value.
- **Open is not absent.** A project can publish before it has settled every question, and should not have to invent an answer to do so, nor let silence pass for a decision. `undecided` names what is still open, with or without the rule that applies meanwhile, so partial adoption is honest and the open questions stay on the agenda.
- **Named, not numbered:** enumerated items carry titles so references stay stable as items change.
- **Nuance goes in `notes`, and `notes` is how the next field gets chosen.** Not every distinction earns an enum. Where a rule can be stated in a sentence, it belongs in the `notes` string of the object it qualifies, which the schema provides on every object that carries a rule, and on `concerns`. That keeps the enums to what a consumer actually branches on, and it leaves a trail: collecting `notes` across adopted files shows which nuances recur, and a nuance that recurs in similar words across many projects is the evidence for promoting it to structure. Structure earned this way is structure the corpus asked for, rather than structure guessed at from a single policy. This repository's own policy is a case in point: it states two concerns no surveyed project cites, that models carry retired and exclusionary language forward and that communities lose the shaping of their own language, in `concerns.notes` only, where they wait for other projects to name them too.
- **"AI" here is shorthand.** These documents say *AI* for brevity, but what the surveyed policies actually govern is generative models, not machine learning at large. **LLM-gen-AI** — the term Fedora's alignment work takes from the Software Freedom Conservancy — is the more precise one, and worth adopting if it settles in the CHAOSS working group's vocabulary; several policies in the [coverage survey](./coverage.md) already scope themselves that narrowly in their own words.

## The format, in brief

Top-level fields; every one is optional, but a file must declare something: a stance, by default or for a single scope, any other AI-specific rule, an open question in `undecided`, or `summary: neutral` for a project with no AI-specific rule. `signoff`, `concerns` and `since` can accompany any of these but do not count on their own: a sign-off requirement predates AI, a motivation changes nothing a consumer does, and a date says when the rules apply, not what they are. To write one, follow [`writing-a-policy.md`](./writing-a-policy.md), which walks through the fields as a sequence of decisions. Each field's meaning is in the [example](./ai-policy.example.yaml); the shape is validated by [`ai-policy.schema.yaml`](./ai-policy.schema.yaml).

| Field | Purpose |
|---|---|
| `version` | The `ai-policy` format version. |
| `summary` | Quick contribution-stance filter (`neutral \| permissive \| mixed \| restrictive \| disallowed`), derived from the stance; optional. |
| `status` | Maturity of the policy itself (`adopted \| draft \| under-discussion`). |
| `since` | The date from which the rules of the file apply, for a consumer that reads a repository's history. |
| `undecided` | Questions not yet settled, each optionally with the rule in force meanwhile. |
| `statement` / `guardrailsRef` | Pointers to the human-readable policy and the actionable guard-rail checklist. |
| `exceptions` | Flags that the structured stance is a summary with carve-outs in `statement`. |
| `concerns` | The societal/ethical motivation (for aggregation): `values` from a shared list, `notes` in the project's words. |
| `defaults` + `assertions[]` | Per-content-type `stance` / `disclosure` / `humanReview` (the contributor's involvement) / `accountability` / `requirements`. |
| `allowedUses` | Explicitly permitted AI uses whose output isn't a contribution. |
| `review` | AI in the project's *review* of contributions: whether it may assist, and whether a human must still decide. |
| `newContributors` | Rules for contributors with no merged contribution yet: the AI stance that applies to them, and human-only "good first issue" tickets. |
| `autonomousAgents` (+ `attestation`) | Agent-autonomy switch and how agents must identify themselves. |
| `priorArrangement` | Contribution kinds needing agreement *before* submission, and what satisfies it. |
| `actorExceptions` | Actors governed differently (a signal, not a resolution layer). |
| `disclosureFormat` | How disclosure is formatted (`trailers` keyed by degree). |
| `enforcement`, `signoff` | Declared enforcement mechanism and the human sign-off (DCO/CLA). |
| `models.policy` | The AI used *in development*: minimum model openness by component (not runtime deps). |

## Resolution

A consumer resolves the effective policy for a contribution by its **`scope`** (content type), each layer overriding only the fields it sets:

- **`defaults`** is the base for every field.
- A `scope` present in **`assertions[]`** overrides `defaults` for that scope only; the fields it omits inherit from `defaults`. A scope *absent* from `assertions[]` resolves from `defaults`, and an omitted `assertions[]` is valid (pure defaults).
- **`actorExceptions`** is *not* part of this per-field resolution: it declares that a named actor is governed differently, and a consumer surfaces it and reads its `notes`/`statement`. Only its concrete `autonomousAgentsAllowed` carve-out is machine-actionable.
- **Whole-file fields do not cascade, and they do not override the stance — they compose with it.** `autonomousAgents`, `priorArrangement` and `review` apply to the file as a whole and answer different questions from `stance`, so a consumer must satisfy each independently rather than picking a winner. `stance` says whether this kind of contribution may be offered at all; `priorArrangement` says whether it may be offered *without agreement obtained first*; `autonomousAgents` says whether a non-human may do the offering; `review` says what the project will do with it afterwards. A change permitted by `stance` and caught by `priorArrangement` is permitted **and** gated, not contradictory.
- Every field is optional, but a file must declare something: a stance, by default or for a single scope, any other rule, an open question in `undecided`, or `summary: neutral` on its own. Real policies govern, say, AI-written issues without a word about code, and a file should not have to invent a default to say so; without a default stance it simply carries no `summary`.
- **`newContributors` tightens, never loosens.** For a contributor with no merged contribution to the project yet, the stricter of `newContributors.stance` and the scope's own stance applies.
- **`summary` is derived, not chosen.** It is a convenience for aggregators that do not resolve the file, so it must agree with the stance field-set, and the schema enforces that: `disallowed` for a default stance of `disallowed`, `restrictive` for `assisted`, and for `generated` either `permissive`, or `mixed` when the file adds an AI-specific condition (a scope held below `generated`, disclosure `required` or `prohibited`, a `requirements` gate, a non-empty `priorArrangement`, or a `newContributors` rule). Agent autonomy does not count, being a separate axis. A summary that is a matter of opinion would be the least clear field in the file.
- **`since` dates the file, not each rule.** A consumer that reads the history of a repository, such as an aggregator comparing a policy with the commits made under it, does not read a contribution made before `since` against the file. Without `since`, it may take the day the file was added. That is often wrong: most projects adopting the file already had a rule in prose, sometimes for months. Changes to a rule after the file exists are dated by the file's own history, so one date is enough. A consumer that checks a contribution about to be submitted ignores it.
- **`summary: neutral` stands alone.** It declares that the project considered AI and decided it needs no rule of its own, as Kubernetes did: the ordinary contribution rules at `statement` govern every contribution, however it was made. A neutral file carries no other AI-specific field, and a consumer applies no AI-specific gate.
- **Open questions carry their interim rule.** A field listed in `undecided` is one the project has not settled. If it also carries a value, that value is the rule in force meanwhile, and a consumer applies it: `undecided: [defaults.stance]` with `stance: generated` means *AI contributions are accepted while we decide*, and with `stance: disallowed` means *not until we have decided*. If it carries no value, there is no interim rule, and a consumer never reads it as permission: where it grants or withholds something (`stance`, `autonomousAgents`, `review`), the restrictive reading applies, and elsewhere the consumer refers to `statement`. A field neither declared nor listed is simply not addressed, and the consumer refers to `statement`.

`defaults` and each `assertions[]` entry share one field-set (`stance`, `disclosure`, `humanReview`, `requirements`), defined once in the [schema](./ai-policy.schema.yaml) as a reusable `$ref`, so "same fields" is a structural guarantee, not a prose claim. The layering above is defined by this spec and applied by the consumer (as a browser applies the CSS cascade); it is never encoded in an individual file.

## Questions for agent-tooling builders

Not "please ratify a standard." **Adoption first**, the [`FUNDING.yml`](#prior-art-related-work) model: a tiny file wins by having a *consumer*, not by being standardized. The questions that matter:

1. Is this the right *shape* for an agent to consume?
2. Would agent tooling actually read a conventional repo file like this, natively or via an MCP server?
3. What is the smallest consumer that would prove it?

## Prior art & related work

- **`FUNDING.yml`** is the closest model: a tiny, single-purpose YAML file that reached wide adoption not by being standardized but by having a *consumer* (GitHub renders it as a Sponsor button). Judge `ai-policy.yaml` the same way.
- **`AGENTS.md` / `CLAUDE.md`** are prose instructions *to* agents. `ai-policy.yaml` is the structured, machine-actionable counterpart, co-located and cross-linked; a *section of* `AGENTS.md` is a plausible alternative home.
- **[ai-policy.dev](https://ai-policy.dev/)** is the prose layer this format points at: a small library of ready-made `AI_POLICY.md` texts (such as *AI Allowed*, *AI Disclosed*, *Human Voice* and *AI Disallowed*) that a project copies into its repository, in the manner of choosealicense.com. Each preset is tagged on the site with rule IDs marked as permits, requires or forbids, but that metadata is [stripped when the policy is copied](https://github.com/43081j/ai-policy/blob/main/policies/_template.md), so an adopting repository publishes nothing a consumer can read. The two compose rather than compete: a preset is a natural `statement` target, and every preset is expressible in this format: [`examples/`](./examples/) holds each one as an `ai-policy.yaml` to ship beside its Markdown, scored in [coverage](./coverage.md#template-policies).
- **[AI Attribution format](https://aiattribution.github.io)** and **[CUSTODY](https://custody-framework.org)** are adjacent but distinct: attribution records *who or what produced* a work; CUSTODY *contains* autonomous agents at runtime. Neither expresses a *contribution policy* (the rules a project sets), but this format's disclosure and `attestation` facets can align with or reference them.
- **["We Permit the Use of AI, but […]"](https://arxiv.org/abs/2609.07542)** (Hora, Robbes and Zacchiroli, 2026) is the largest study of these policies so far: 281 policies from GitHub's most-starred projects, coded along six dimensions, with the [labelled corpus](https://doi.org/10.5281/zenodo.22212208) published under CC BY 4.0. It proposes no format, but its dimensions map onto this one's fields, and its counts settled two of its design questions, what a disclosure must state and the split between involvement and accountability. Its authors name the gap this format addresses: tool and platform builders have "no disclosure convention to target". [`coverage.md`](./coverage.md#a-larger-corpus-popular-projects) maps it field by field, including how the dedicated policy files it tracked have changed.
- **["To Ban or not to Ban?"](https://arxiv.org/abs/2603.26487)** (Yang, He and Zhou, 2026) studies how 67 highly visible projects govern generative-AI contributions, and argues that governance must cover accountability, verification, review capacity, code provenance and platform infrastructure. The first four have fields here: `accountability`; `humanReview` and `requirements` for verification; `priorArrangement`, `newContributors` and `enforcement` for review capacity; and the `provenance-attested` requirement and `ip-provenance` concern for code provenance. Platform infrastructure is the [forge-level record](#open-questions) this format leaves open.
- **["Making AI Visible, Not Vanished"](https://arxiv.org/abs/2608.03329)** (Chen, Zimmermann and Trinkenreich, 2026) finds 385 projects with AI policies among 29,624 repositories, describes them along five dimensions (transparency, responsibility, attribution, constraints, enforcement), and is the first study to measure what adopting a policy does. It finds that AI governance "primarily regulates rather than prohibits AI-assisted development", and that policies stressing transparency and responsibility do better than restriction alone. That is evidence for the format's premise: disclosure and responsibility rules, which most policies centre on, are worth making machine-readable.
- **[IETF machine-readability draft](https://datatracker.ietf.org/doc/draft-vaughan-machine-readability/)** is a rubric (parseable / interpretable / discoverable / actionable / verifiable) this format is evaluated against in **[`machine-readability.md`](./machine-readability.md)** (parseable, discoverable, actionable today; interpretability the open gap).

## Open questions

Format & tooling:

- **Smallest consumer:** the reference reader/validator (a CLI, a CI action, or an MCP server) that would prove the format is worth adopting.
- **Interpretability `@context`:** the JSON Schema ([`ai-policy.schema.yaml`](./ai-policy.schema.yaml)) makes the format parseable and the stance field-set a shared `$ref`; the open gap ([machine-readability.md](./machine-readability.md)) is binding each enum to a shared, dereferenceable vocabulary (a JSON-LD `@context`) for full *interpretability*.
- **Template provenance:** should a declaration say which published template its prose was adopted from, and at which version (for example an [ai-policy.dev](https://ai-policy.dev/) preset)? Copied policy text drifts from its source silently, as copied licence texts did before SPDX identifiers; a `basedOn` reference would let a consumer compare like with like and an aggregator count adoption per template. It needs a template publisher that versions its presets, which none yet does.
- **Organisation-level policy:** can a repository inherit a policy its organisation publishes once? Projects already link an organisation-wide `LLM_POLICY` from each repository ([coverage](./coverage.md#a-larger-corpus-popular-projects)), and a forge-wide default repository (GitHub's `.github`) is the obvious home. Inheritance needs a precedence rule, repository over organisation per field or per file, and a consumer has to know it is reading an inherited policy rather than a missing one.
- **Peer-record discovery:** the registered `type` string and pointer shape for records (e.g. a `publiccode.yml` `externalMetadata` entry) that reference this file.

Field-level:

- **Scope vocabulary:** is the `scope` set extensible enough (moderation, meeting/transcription bots, finer splits)? Review has been taken out of this question and given its own field, because it is done *to* a contribution rather than being one and so was never a content type. What remains open is narrower and mostly about whether the existing splits are principled: Gitea permits AI to draft issues and pull requests while banning it in replies to reviewers, a line the vocabulary happens to reproduce (`issue-descriptions` and `pull-request-descriptions` on one side, `comments` on the other) without modelling the reason, which is composing versus conversing. It works today; it may not survive a project that splits differently.
- **`review` depth:** the field carries `aiAssist`, `humanDecision` and a `notes` string. Rust's requirement that review bots run under separate blockable accounts with non-blocking comments, and Flathub's ban on a contributor *requesting* an AI-agent review, are sentences in `notes` for now. If either recurs across several projects in comparable words, it is a candidate for promotion.
- **A forge-level record:** platform self-commitments, hosting restrictions and governance-process rules are [out of scope here](#what-this-format-does-not-govern) and have no carrier at all. Codeberg's undertaking never to train on hosted code is the clearest instance, and the CHAOSS domains that score as ungoverned across projects are mostly of this kind. Whether this project should specify that record, or only name the gap, is open. If one is built, this format gains a companion rather than a field, and both will then need to say which kind of document they are.
- **`undecided` granularity:** the list names whole-file fields and the `defaults` field-set, so a project cannot yet say that its stance on `code` is settled while its stance on `docs` is open, or that one actor exception is under discussion. Per-scope entries would need a path syntax into `assertions[]`; whether any project needs that before it can publish is untested.
- **Sanctioned-workflow pointer:** should a declaration point at a library of approved agent workflows, such as [Fedora's skills library](https://forge.fedoraproject.org/ai-ml/skills-library)? `guardrailsRef` points at rules a contributor must observe; a skills library is the opposite direction, naming what the project has already blessed. Folding both into one pointer may be right, but the semantics differ. A single skill can also carry out one rule of the policy: shap keeps an [AI-disclosure skill](https://github.com/shap/shap/blob/976466af353e68df551a4b73db45ef41ceca8b13/.claude/skills/ai-disclosure/SKILL.md) in its repository that has the agent record its own level of involvement, which is `disclosureFormat` implemented on the agent's side.
- **Stance ordinality:** is `disallowed < assisted < generated` genuinely ordinal for all projects?
- **Enforcement consequence:** should `enforcement.consequence` be structured, or stay in `statement`?
- **`models.policy` vs `requirements`:** should model-provenance requirements fold into `requirements`?
- **`requirements` altitude:** should it list only genuinely AI-specific gates and leave universal ones (tests, CI) to the general contribution process? Godot shows why the boundary needs watching: its June 2026 rewrite was driven by AI pressure and the review backlog together, and the resulting document bars new contributors (three or fewer merged pull requests) from features and significant refactors without maintainer permission — a mentorship and trust rule that applies whatever tools are used, stated before the AI section. A policy revised *because of* AI can carry rules that are not AI rules, and those belong to the general contribution process.
- **Structuring the guard-rail prose:** should the `guardrailsRef` checklist be structured, not just pointed at?
- **Attestation placement:** should `attestation` be expressible per-scope (stricter identity in security paths)?
- **`priorArrangement` shape (settled in principle, open in detail):** the gate itself is now a field, added because four adopted policies require it — Debian (bulk changes, prior discussion), Rust (a reviewer agreeing before an LLM-created pull request is opened), Fedora (large-scale initiatives to the Council), Polars (an already-accepted issue). Because most of these gate the *human* path, it sits outside `autonomousAgents` and covers both. What remains open is its shape where a project gates two kinds of contribution differently: `appliesTo` is a list while `basis` is single, so Debian's *bulk changes to discussion* and Rust's *AI-generated pull requests to reviewer agreement* cannot both be stated in one file. Making `basis` a list would not fix that; the shape needed pairs a basis with each trigger. Two smaller gaps: `agent-submissions` and `ai-generated-prs` are not distinguished, though an agent's pull request is normally both, and `bulk-changes` may not belong at all, since mass-change conventions predate LLMs and outlive them.
- **Disclosure by forge label:** should `disclosureFormat.method` gain a `label` value? Rust marks merged LLM-created pull requests `llm-assisted`. Unlike a trailer or a PR template it is applied by the reviewer at merge, which makes it a measurement instrument as much as a disclosure.
- **Contributor opt-out / non-discrimination:** should the format declare that contributors may not be *coerced* into using AI, and won't be shamed for opting in or out? The reverse commitment turns up too: ai-policy.dev's *Human Responsible* preset promises that a contributor's own tooling "is not policed, will not be asked about, and does not need to be shared". That is a promise of non-inquiry, distinct from `disclosure: prohibited`, which only governs what the submission may carry.
- **`allowedUses` conditions:** should each permitted use carry a condition (e.g. research/debugging only where output isn't contributed)?

Decided for now, kept here because new evidence would reopen them:

- **Numeric thresholds.** Significance thresholds stay in prose; no field. Two policies state one mechanically, but they differ in kind and only one is consumable: Godot presumes code under fifteen lines trivial, which an agent holding a diff can evaluate, while Rust's circuit-breaker (halt LLM-created merges above half of merged pull requests over six weeks) needs project-wide merge history no contributor or agent has, and answers whether the door is currently open rather than whether a change complies. The test that settled it generalises to any future candidate that looks countable: **a threshold earns a field only if a consumer can evaluate it before submitting.** On that test the evidence is a single project, against a deliberate design choice and seven policies drawing the line qualitatively. *Reopen if:* further projects publish per-contribution thresholds a submitter could check, and they converge on a comparable unit — several more line counts, or a shared measure that is not line counts. Divergent units would confirm the prose choice rather than undermine it.
